# C14 technical report: inventory analysis freshness

The backend uses one tenant-scoped selector for creation and comparison. `inventory.selection.v1` compares normalized typed records and review state against a hash-checked saved request. Change groups contain exact totals and at most 20 examples each; explicit counts expose replacement requirements without substitution. Comparison limits are 10,000 rows including recipe lines and 8 MiB of input data. Invalid, unsupported or oversized comparisons return unknown.

The HTTP analysis read adds no-store freshness metadata to the historical receipt. The service receipt read and idempotent creation response remain exact. Portfolio and advisor reads withhold stale/unknown numeric results and provenance, while preserving links and scope. Saved case contexts remain immutable. A single repeatable-read transaction scopes each comparison. Recipe lines are loaded with a shared bounded query.

The final suite passed **313 tests**, with **one real-OCR skip**, in 543.21 seconds. The final focused suite passed **36 tests** in 129.54 seconds; Ruff and whitespace checks passed. Final review added typed result/scope validation and safe unknown summaries for malformed results, without claiming a result-integrity hash. See [run evidence](../runs/inventory-freshness-2026-10-11/README.md) and [the contract](../research/INVENTORY_FRESHNESS.md). No schema change beyond migration 14, real model inference, document OCR, statistical forecast or business-data processing is claimed. Freshness describes recorded input equality and deliberately does not reverify source bytes or infer missing events. The owner interface remains deferred; full capacity, recovery and accounting acceptance remain open.
