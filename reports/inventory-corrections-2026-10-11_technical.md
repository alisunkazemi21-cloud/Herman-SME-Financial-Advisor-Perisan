# C13 technical report: reviewed inventory corrections

Migration 14 adds predecessor links to records/approvals, same-business referential integrity, a unique approved-successor index, header transaction stamps and structural guards. New typed details, recipe lines and import origins must share the unreviewed header's creation transaction. Deferred checks require complete typed data; approval derives the link and checks structure. Legacy headers cannot acquire late children. Stored earlier results and source rows are not rewritten.

The correction endpoint uses a discriminated typed request for counts, movements, recipes and fulfillments. It preserves the existing pure inventory model shape. Proposal/approval require a current approved same-kind predecessor; competing candidates can exist but only one can win. Evidence bytes are checked before proposing and approving corrections. Detail/list reads expose lifecycle and lineage; lists have state/kind/predecessor filters and UUID cursors.

Current reconciliation excludes superseded records and unapproved corrections before period selection. It retains independent unreviewed inputs as incomplete data. Stale count selectors return the latest approved successor ID but require explicit replacement by the caller. Duplicate matching excludes the correction's own ancestry and competing versions, while retaining independent candidates. Imported source-row uniqueness remains enforced.

Each new analysis records bounded correction provenance separately from direct import provenance: at most 64 correction links, 10,000 rows and 8 MiB. Old source metadata stays distinguishable from current corrected inputs. Context retrieval includes the stored receipt and retains its 64 KiB response bound. Existing analyses are historical snapshots; automatic freshness/impact reporting is not yet implemented.

The focused correction suite passed 26 checks in 67.79 seconds before a final import-origin guard test was added. The earlier correction/backend/import run passed 34. Coverage includes independent stock/consumption expectations for all four record kinds, time/validity changes, rejected candidates, duplicate decisions, concurrent reviews, immutable earlier results, inherited import rows, retry behavior, roles, API validation, count selection and direct SQL structural guards. The full PostgreSQL suite passed **277 tests**, including all 27 new correction cases, with **one real-OCR skip**; Ruff and whitespace checks passed. The final record-detail no-store and exact-decimal response adjustments passed two focused API/backend tests in 8.87 seconds.

A targeted probe demonstrated acceptance of excess recipe-yield fractional precision before the fix. The existing tuple-based Decimal precision validator now rejects it before persistence; valid trailing zeros and the calculator formula remain unchanged. This checkpoint does not establish semantic matching, real OCR/model quality, statutory compliance, operational recovery/capacity or the deferred UI.
